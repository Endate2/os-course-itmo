## Задание

Для оптимизации работы с блочными устройствами в ОС существует кэш страниц с
данными, которыми мы производим операции чтения и записи на диск. Такой кэш
позволяет избежать высоких задержек при повторном доступе к данным, так как
операция будет выполнена с данными в RAM, а не на диске (вспомним [пирамиду памяти][memory-pyramid-csbasics]
на 35 слайде и [всё-всё][what-every-programmer-should-know-about-memory]).

## Краткий обзор кода

### Структура проекта

| Файл | Назначение |
|---|---|
| `vtpc.h`, `vtpc.c` | Пользовательский API: `open`, `close`, `read`, `write`, `lseek`, `fsync` с той же сигнатурой, что и в libc |
| `util.h`, `util.c` | Ядро кэша: хранение страниц, поиск, вытеснение, упреждающее чтение |
| `sys.h` | Обёртки над системными вызовами через `syscall()`, без высокоуровневых функций libc |

### Основные структуры

- `struct vtpc_page` — страница кэша размером 4 КБ. Хранит флаги `use` (занята), `ref` (бит обращения), `dirty` (изменена), число валидных байт `valid`, а также указатели для очереди вытеснения и цепочки хеш-таблицы.
- `struct vtpc_file` — описание открытого файла: системный дескриптор, текущая позиция, размер и состояние readahead.

Кэш — статический массив из 256 страниц (`VTPC_CACHE_PAGES`). Буферы выделяются через `posix_memalign` с выравниванием 4096 байт, так как файлы открываются с `O_DIRECT`, в обход страничного кэша ОС. Для быстрого поиска страницы по паре (файл, номер блока) используется хеш-таблица с цепочками.

### Алгоритм вытеснения Second chance

Все занятые страницы стоят в FIFO-очереди. При обращении к странице из кэша ей ставится `ref = true`. Когда свободных слотов нет, просматривается голова очереди:
- если `ref = true`, бит сбрасывается и страница переносится в хвост (получает «второй шанс»);
- иначе страница становится жертвой. Если она грязная, сначала записывается на диск.

```c
static struct vtpc_page* vtpc_second_chance_algo(void) {
  while (head != NULL && head->ref) {
    struct vtpc_page* p = head;
    p->ref = false;
    vtpc_throw_page(p);   // убрать из головы
    vtpc_reset_tail(p);   // поставить в хвост
  }
  return head;
}
```

### Загрузка страниц

- `vtpc_get_page` ищет страницу в хеш-таблице. При промахе берётся свободный слот, а если его нет — вытесняется страница по Second chance.
- Если блок будет перезаписан целиком, чтение с диска не выполняется (`need_disk = false`).
- **Упреждающее чтение:** при последовательном доступе заранее подгружается окно страниц одним `pread`. Окно начинается с 4 страниц и удваивается до 32. Когда чтение доходит до маркера в середине окна, загружается следующее окно.

### Запись на диск

Грязные страницы сбрасываются при вытеснении и при `fsync`; при `close` страницы файла ещё и освобождаются. Из-за `O_DIRECT` запись идёт блоками, кратными размеру страницы. Поэтому после неё файл обрезается `ftruncate` до реального размера.

Доступ к общим структурам кэша защищён глобальным мьютексом.

## Методика тестирования

### Программа-нагрузчик

Для проверки кэша написана программа-нагрузчик `bench` (`bench/bench.c`). Она работает с файлами только через `open`, `read`, `write`, `lseek`, `fsync` и `close`. Библиотека подключается к ней через `LD_PRELOAD` и перехватывает все эти вызовы, поэтому код нагрузчика одинаков для всех конфигураций.

Нагрузчик собирается без `_FORTIFY_SOURCE`. Иначе компилятор заменяет `read` на `__read_chk`, и такой вызов прошёл бы мимо библиотеки.

Для каждого прогона нагрузчик измеряет через `clock_gettime` и `getrusage`:
- `wall` — общее время работы;
- `user` — время в режиме пользователя;
- `sys` — время в режиме ядра;
- `inblk` / `outblk` — сколько блоков по 512 байт реально прочитано с диска и записано на него;
- `ctxsw` — число добровольных переключений контекста, примерно равное числу блокирующих операций ввода-вывода.

Замер охватывает весь цикл работы с файлом, от `open` до `close`. В него входит сброс грязных страниц при `fsync` и `close`.

Нагрузчик также проверяет корректность:
- `cksum` — контрольная сумма прочитанных данных.

Режимы работы нагрузчика:

| Режим | Что делает |
|---|---|
| `gen FILE --size N` | Создаёт файл заданного размера с псевдослучайными данными |
| `drop FILE` | Выбрасывает файл из страничного кэша ОС (`posix_fadvise(POSIX_FADV_DONTNEED)`) |
| `seq FILE --bs N` | Последовательное чтение блоками по `N` байт |
| `hot FILE --bs N --hot S` | Случайное чтение блоков внутри «горячей» области размером `S` в начале файла |
| `rand FILE --bs N` | Случайное чтение блоков по всему файлу |
| `write FILE --bs N --total S [--rand]` | Запись блоками по `N` байт в область размером `S`: последовательно или вразброс, в конце `fsync` |

Флаг `--direct` включает режим без какого-либо кэша. Файл открывается с `O_DIRECT`, поэтому невыровненное чтение расширяется до границ блока 4 КБ. Невыровненная запись выполняется как чтение-изменение-запись целого блока.

### Конфигурации

Библиотека собирается в четырёх вариантах с помощью макросов `VTPC_USE_O_DIRECT` и `VTPC_RA_ENABLED`. Вместе с двумя режимами без библиотеки получается шесть конфигураций:

| Конфигурация | Кэш ОС | Мой кэш | Readahead | Как запускается |
|---|---|---|---|---|
| `nocache` | нет | нет | — | `bench ... --direct` |
| `oscache` | да | нет | только ОС | `bench ...` |
| `vtpc` | нет | да | да | `LD_PRELOAD=libvtpc.so` |
| `vtpc_nora` | нет | да | нет | `LD_PRELOAD=libvtpc_nora.so` |
| `vtpc_os` | да | да | да | `LD_PRELOAD=libvtpc_os.so` |
| `vtpc_os_nora` | да | да | нет | `LD_PRELOAD=libvtpc_os_nora.so` |

Перед каждым прогоном тестовый файл выбрасывается из кэша ОС, то есть все запуски начинаются с холодного кэша. 

### Сценарии

Тестовый файл имеет размер 256 МБ. Мой кэш вмещает 256 страниц, то есть 1 МБ.

**Благоприятные для моего кэша:**

| Сценарий | Нагрузка | Что проверяет |
|---|---|---|
| `seq4k` | Последовательное чтение всего файла блоками по 4 КБ | Работу readahead: без него каждая страница — отдельное синхронное чтение с диска |
| `seqsmall` | Последовательное чтение 8 МБ блоками по 128 байт | Мелкие чтения: на одну страницу приходится 32 обращения, и все, кроме первого, — попадания |
| `hot` | 100 000 случайных чтений по 4 КБ внутри первых 512 КБ файла | Рабочее множество меньше кэша |
| `smallwrite` | Последовательная запись 2 МБ блоками по 64 байта | Накопление мелких записей в странице и сброс на диск целыми блоками |
| `hotwrite` | 30 000 записей по 64 байта в случайные места области 256 КБ | Отложенную запись: многократная перезапись одних и тех же страниц в памяти |

**Неблагоприятные:**

| Сценарий | Нагрузка | Что проверяет |
|---|---|---|
| `rand` | 20 000 случайных чтений по 4 КБ по всему файлу | Рабочее множество в 256 раз больше кэша: почти каждое обращение — промах, кэш даёт только накладные расходы |
| `seq1m` | Последовательное чтение всего файла блоками по 1 МБ | Крупные запросы: ОС обслуживает их одним системным вызовом, а мой кэш дробит их на страницы и копирует данные дважды |


### Параметры прогона

- Размер тестового файла: 256 МБ (`FILE_MB=256`).
- Повторов на каждую пару «сценарий × конфигурация»: 10 (`REPEAT=10`), всего 420 запусков.
- Кэш ОС перед каждым запуском сбрасывался (`bench drop`), то есть все запуски холодные.
- Запуск: `sudo nice -n -5 taskset -c 2 env FILE_MB=256 REPEAT=10 ./run.sh`.

## Заключение

В работе реализован блочный кэш в пространстве пользователя с алгоритмом вытеснения Second chance и упреждающим чтением при последовательном доступе. Кэш подключается к любой программе через `LD_PRELOAD` и работает с диском в обход кэша ОС через `O_DIRECT`. Корректность подтверждена совпадением контрольных сумм во всех 420 запусках.

Результаты эксперимента:

1. **Кэш эффективен, когда обращения повторяются или мельче страницы.** На мелких чтениях и записях, а также на рабочем множестве, помещающемся в кэш, программа с кэшем работает в 49–425 раз быстрее, чем без кэша, а время в режиме ядра сокращается практически до нуля.
2. **Мой кэш выигрывает у кэша ОС на попаданиях**, потому что не делает системных вызовов: на горячем множестве на 30 %, на многократной перезаписи одних страниц в 3.3 раза. На первичном чтении с диска кэш ОС быстрее за счёт асинхронного чтения и более крупного адаптивного readahead.
3. **Упреждающее чтение необходимо для последовательного доступа.** Без него кэш на последовательном чтении не даёт никакого выигрыша по сравнению с работой без кэша; с ним время сокращается в 3.2 раза.
4. **Кэш бесполезен или вреден**, когда рабочее множество намного больше кэша или когда программа сама читает крупными блоками
